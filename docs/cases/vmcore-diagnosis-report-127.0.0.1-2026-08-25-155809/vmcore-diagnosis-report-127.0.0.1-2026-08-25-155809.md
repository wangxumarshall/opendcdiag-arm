# 内核转储诊断报告

**转储**：`127.0.0.1-2026-08-25-15:58:09/vmcore`（9.98 GB，kdump, arm64）
**内核**：6.6.0-145.3.23.154.oe2403sp3.aarch64（KASLR 开启）
**机型**：Yangtze Computing R240K V2 / BC82AMQA（HISI HIP08 平台，8 NUMA × 24 CPU = 192 核）
**分析工具**：crash 8.x + 精确匹配版本 debuginfo/source；objdump -dl 反汇编对照 DWARF 行号
**报告日期**：2026-08-25　　分析会话：ox-alpha

---

## 1. 执行摘要

本机于 2026-08-25 15:58 发生内核 panic：CPU 179 上的 kworker 在调度器负载均衡路径
`find_busiest_group+0x140` 解引用野指针 `0x00ffb34569fc3ac0`（level-0 翻译故障）。

经指令级现场重建、四则代数闭合验证与**寄存器-vs-内存对照实验**，结论如下：

> **根因（最深可证层）**：CPU 179 物理核的取数数据通路存在间歇性硬件故障——
> 从内存加载数据时，加载结果与内存真实内容不一致（内存内容经转储逐字验证完好）。
> 本次 panic 的直接死因是一条 `LDR X20, [X0, W25, SXTW #3]`（读取只读数组
> `__per_cpu_offset[146]`）返回了错误数据 `0x00ffffcc879da2e0`，而内存真值为
> `0xffffcc879ed92000`；错误的偏移量被加到正确的 `&runqueues` 上生成野指针，
> 随后 `LDR X23, [X27, #0x120]` 触发翻译故障并 panic。

这不是软件缺陷。同一台机器自 08-14 以来的 **5 次开机、78 起同类事件（73 次"虚假翻译故障"
WARNING + 5 次 Oops panic）无一例外全部发生于 CPU 179**，其余 191 个核零事件；
两次 panic 的腐化模式互不相同但同属"加载返回错误数据"；且近期开机首症时间显著缩短
（29h → 47h → 14min → 28min → 7min），呈**渐进性恶化**特征。建议立即将 CPU 179 下线隔离并
安排整机/CPU 硬件检修（RMA），详见 §10。

## 2. 崩溃现场还原

```
[418.373008] Unable to handle kernel paging request at virtual address 00ffb34569fc3ac0
[418.389628]   EC = 0x25: DABT (current EL), FSC = 0x04: level 0 translation fault
[418.546640] CPU: 179 PID: 1931 Comm: kworker/179:1H  Workqueue: kblockd
[418.578439] pc : find_busiest_group+0x140/0xb60
Call path: worker_thread → schedule → __schedule → pick_next_task
           → pick_next_task_fair → newidle_balance → load_balance → find_busiest_group
Code: f9400782 f879d814 2a1903e0 8b14003b (f9409377)
```

故障指令解码：`f9409377` = **`LDR X23, [X27, #0x120]`**。

结合反汇编与 DWARF 行号（kernel/sched/fair.c），该点为 `find_busiest_group()` 中
`for_each_cpu_and(i, sched_group_span(group), env->cpus)` 循环体内联展开的
`cpu_load(rq)`（fair.c:5024 → `cfs_rq_load_avg(&rq->cfs)`），其中：

```asm
; fair.c:12050  rq = cpu_rq(i) 的内联展开：
ae34: ldp  x0, x1, [sp, #8]        ; x0 = &__per_cpu_offset, x1 = &runqueues
ae3c: ldr  x20, [x0, w25, sxtw #3] ; x20 = __per_cpu_offset[i]      ← 数据源
ae44: add  x27, x1, x20            ; x27 = cpu_rq(i)
ae48: ldr  x23, [x27, #0x120]      ; ← 故障指令；offsetof(struct rq, cfs.avg.load_avg)=0x120
```

符号解析确认（crash `sym`）：运行时 `x1 = 0xffffb378e25e96c0 = runqueues`，
`[sp,#8] = 0xffffb378e29e55d0 = &__per_cpu_offset`，`i = w25 = x25 = 146`。

## 3. 推理链 A：寄存器代数——唯一异常值是 x20

崩溃时 pt_regs（由 el1 入栈帧三处独立副本交叉验证一致）关键值：

| 寄存器 | 值 | 含义 | 判定 |
|---|---|---|---|
| x1 | `ffffb378e25e96c0` | `&runqueues` | ✅ 与 KASLR 基址精确吻合 |
| x20 | `00ffffcc879da2e0` | 加载所得 `__per_cpu_offset[146]` | ❌ **非规范地址，腐化** |
| x27 | `00ffb34569fc3ac0−0x120` | x1+x20 计算结果 | 代数精确成立 |
| x21 | `ffffb378e29dfcb0` | `&nr_cpu_ids` | ✅ |
| x24 | `ffffb378e29e5000` | `&__per_cpu_offset−0x5d0` | ✅ |

**验证**：本开机 KASLR 文本/数据偏移 δ₁₅₅₈ = `0x337860A80000`
（独立来源：pc − 符号静态地址）。逐项检验：

- `&runqueues(静态 ffff800081b696c0) + δ = ffffb378e25e96c0 = x1` ✅ 精确
- `x27 − x20 = 0xFFFFB378E25E96C0 = x1` ✅ **代数闭合**
- `x21、x24` 同法验证均精确吻合 ✅

⇒ 除 x20 外全部寄存器与机器状态自洽；**x27 是 x1+x20 的忠实计算结果，
唯一的原始错误数据是 x20 —— 即那条从内存加载 `__per_cpu_offset[146]` 的指令的返回值**。
栈污染假设被排除（x0、x1 为相邻 `ldp` 双字加载，x1 正确；env 指针 x19 及整帧结构完好）。

同样的代数在另外三次同点 panic 中全部独立闭合（详见 §7 表）：四次 `x27 ≡ x1 + x20`
无一例外精确成立，且 x1 均正确——腐化始终发生在"从内存加载偏移量"这一步。

## 4. 推理链 B：寄存器 vs 内存对照实验（决定性证据）

`__per_cpu_offset[]` 在启动早期由 `setup_per_cpu_areas()` 填写一次，此后**永不改写**。
对本次转储直接读取该数组内存：

| 下标 | 内存真值（crash 实测） | 寄存器实收值 | 判定 |
|---|---|---|---|
| [0] | `0xffffcc879da2e000` | — | 健康（页对齐，步进 0x22000） |
| **[146]** | **`0xffffcc879ed92000`** | **`0x00ffffcc879da2e0`** | **❌ 不一致** |
| [145]/[147]/[176]/[178]/[179] | 均 `0xffffcc87_9xxx_x000` 形态 | — | 全部健康 |

**内存是对的，寄存器收到的数据是错的。** 腐化不在存储介质、不在数组内容、
不在软件写入，而在 **CPU 179 把数据从缓存/内存搬入寄存器的通路本身**。

更精细的形态学：腐化值恰等于
`entry[0] = 0xffffcc879da2e000` 的字节流右移一字节
（LE 字节序 `00 e0 a2 9d 87 cc ff ff` → 取第 1..8 字节 `e0 a2 9d 87 cc ff ff 00`）。
即该次加载的数据像是从行内**错位一个字节**处组装的——指向 LSU 字节通道/对齐网络级故障，
而非随机位翻转。（entry[0] 与请求的 entry[146] 不同槽位这一事实进一步说明
错误发生在数据组装/返回阶段，而非简单的地址译码错位。）

### 对照案例：16 分钟前的上一次转储（127.0.0.1-2026-08-25-15:42:24）

同一条指令、同一寄存器角色，另一开机、另一下标（i=176）：

| 项目 | 15:42 开机 panic | 15:58 开机 panic（本案） |
|---|---|---|
| 请求加载 | `__per_cpu_offset[176]` | `__per_cpu_offset[146]` |
| 内存真值 | `0xffffda55e61ce000` ✅ | `0xffffcc879ed92000` ✅ |
| 寄存器实收 | `0x0000000000000000` ❌ | `0x00ffffcc879da2e0` ❌ |
| 腐化形态 | 整字读零 | 字节右移一位 |
| FSC | level-3 翻译故障（PTE=0，因 rq 指针=&runqueues+0） | level-0 翻译故障（非规范地址） |
| KASLR 校验 | δ=0x25AA19A40000，x1/x21/x24 全部精确吻合 ✅ | δ=0x337860A80000，同上 ✅ |

两案腐化模式不同构 ⇒ 不是某个固定软件路径的确定性产物；同属一类 ⇒ 共同物理根源。

## 5. 现场其余状态的完整性核验（软件侧无异常）

- **调度域树**：CPU179 rq（`rq->cpu=179`）四级域链 parent/groups 全部健康；
  panic 时 env.sd 为第三级域，其 `groups = 0xffff604003e26c00` 与 pt_regs 中 x22/x26
  **精确一致**；实测该 group 的 cpumask 位图 = `0xffffffffffff0000<<128`，即
  **CPU 144–191（节点 6+7，恰 48 核）**，与 group_weight=48 一致，同时包含 i=146 与
  本机 CPU179——循环取值完全合法。无 UAF/poison/断链迹象。
- **RAS/GHES/EDAC/BERT**：本开机零硬件错误上报（APEI firmware-first 已启用、
  ghes_edac 就绪、SDEI NMI watchdog 注册）。与既往研究结论一致：核内数据通路软故障
  以普通 DABT(EC=0x25) 呈现而非 SError，处于全部 RAS 上报链覆盖之外。
- **kdump 捕获失真假设排除**：硬件 FAR 与保存寄存器代数一致
  （FAR = x27+0x120 精确成立）；pt_regs 与 die/__do_kernel_fault/do_mem_abort 各帧
  三份独立副本相同。

## 6. 鉴别诊断：软件假设逐一裁决

| # | 软件假设 | 裁决 | 依据 |
|---|---|---|---|
| 1 | `__per_cpu_offset[]` 被写坏（UAF/越界/DMA） | ❌ 排除 | 数组启动后无任何代码路径改写；转储实测全表健康且与两次开机各自布局严格规律（步进 0x22000/0x22000）；DMA 写内核 .data 无可能目标 |
| 2 | 栈溢出/栈破坏喂给 x0/x1 错基址 | ❌ 排除 | x0、x1 由相邻 `ldp` 一并加载，x1 经 KASLR 反推精确正确；调用链各帧回溯完好 |
| 3 | cpumask/索引 i 计算错误 | ❌ 排除 | i=146 属 sched_group span∩env->cpus 合法成员（§5）；掩码类寄存器（x5=~0x3FFFF、x17=0xC00000000000 等）均为正常常量形态 |
| 4 | 内核已知 bug（fair.c/load_balance 竞态） | ❌ 掆除 | 四次 panic 值互不相同且含非规范地址，无确定性错误模式可对应任一上游缺陷；同一二进制在其余 191 核累计数千 CPU·天无一事发 |
| 5 | kdump 保存寄存器失真 | ❌ 排除 | §5 第三条 |
| 6 | 编译器/二进制错误 | ❌ 排除 | 故障点直线代码语义平凡；vmlinux 反汇编与源码行号一一对应；五次开机同镜像仅 CPU 事发 |
| 7 | 内存条/SoC 互连故障 | ❌ 排除（正向论证） | 若 DRAM/互连坏，读方不止一个核：同节点其余 23 核共享内存控制器与 HHA，零事件；且腐化具字节错位等微结构特征而非随机位翻转；Hisilicon RAS 对 SoC 层全覆盖而无告警 |

**没有任何软件解释能够同时满足：内存真值正确 + 寄存器实收错误 + 事件 100% 钉死在同一物理核 +
跨开机的两种不同腐化形态 + RAS 全静默。**

## 7. 同机历史事件全景（5 次开机，全部 CPU 179）

| 开机（转储） | 首症 uptime | WARNING× | panic 现场 | panic 坏址（形态） |
|---|---|---|---|---|
| 08-14 19:07 | 104485s（29h） | 12 | `find_busiest_group+0x140`（i=176） | `d936bc836a4a97df`（x20=高低半字拼接） |
| 08-17 13:47 | 169175s（47h） | 26 | `find_busiest_group+0x140`（i=175，swapper idle balance） | `00ffd780f5a3a7c0`（00ff 前缀） |
| 08-24 18:03 | **835s（14min）** | 34 | `bio_add_page+0xf0`（块层，x3 应为合法 bvec 指针，实收全垃圾） | `003c521da2e9b99f`（非规范） |
| 08-25 15:42 | 1707s（28min） | 1 | `find_busiest_group+0x140`（i=176） | `ffffa5aa9b5a97e0`（x20 读作 0） |
| 08-25 15:58 | **418s（7min，首症即 panic）** | 0 | `find_busiest_group+0x140`（i=146，本案） | `00ffb34569fc3ac0`（00ff 前缀） |

要点：

1. **78 起事件（73 WARNING + 5 panic）、5 次开机、数周跨度，100% 发生于 CPU 179，其余 191 核零事件。**
   软件竞态无法跨 reboot 稳定钉死于单一逻辑 CPU；只有物理核属性可以。
2. WARNING 类事件（openEuler 补丁"忽略虚假内核翻译故障"，73 起）全部是对
   **线性映射区合法地址**（`PA | 0xffff000000000000`，如 `ffff6040…`=节点 6 内存）的
   level-0 翻译故障。线性映射 PGD/PUD/PMD 自启动建立后永不改写——软件上不存在
   "未映射"的可能；唯一解释是 MMU 页表遍历读取页表项瞬间拿到错误数据。
   即：**LSU 加载与 PTW 页表遍历两条独立数据返回路径都受同一核内故障影响。**
3. panic 点随当时在跑代码而异（调度器 4 次、块层 1 次）——符合"任意在飞加载皆可中招"
   的随机命中模型；调度器 newidle_balance 因每 CPU kworker 空闲即触发高频执行而成为
   最常见命中点。
4. **首症时间趋势：29h → 47h → 14min → 28min → 7min。** 近三次开机均在半小时内发病，
   最新一次 7 分钟即 panic——呈明显渐进恶化，符合硅片退化（degradation）特征。
5. 附注（诚实披露的两处未决细节）：
   - 08-14/08-24 两案中 FAR 高字节与 pt_regs 中对应基址寄存器高字节相差一个字节
     （如 x3=`55…` 而 FAR=`00…`），提示发作窗口内**多条数据移动相继受扰**（含异常
     保存路径），具体时序无法从转储进一步分辨；不影响主结论（该两案 x20/x3 本身即为
     铁证级错误值）。
   - 精确到微架构子块（LSU 字节对齐网络 / L1d Data RAM 读出列 / ST-FWD /
     公共数据返回总线）超出 vmcore 证据能力边界，需厂商 JTAG/at-speed 扫描定位。

## 8. 与既往研究及现场处置记录的一致性

- 本机为既定研究对象：既往会话已通过"寄存器 vs 内存对照 + 三臂活体实验 +
  gem5 故障注入建模"判定该核为 mercurial core（L1d 数据通路软故障）。本案以
  **完全独立的新证据**（四次代数闭合 + 两次内存对照铁证）复现并加固了同一结论。
- 08-25 当天站点曾加载自制 out-of-tree 模块 `l1d_disable`，通过清 `SCTLR_EL1.C`
  在 CPU 179 上反复开关 D-Cache（51302s–63485s 区间多次 toggle）。注意：
  ① 该缓解实验期间及之后（模块卸载 3.7 小时后）仍发生 panic（15:42 案）；
  ② 15:58 案所在开机根本未加载该模块；
  ③ 08-14/17/24 三次开机故障均先于任何实验存在。
  ⇒ **清 C-bit 不能规避该故障**（故障不局限于可被 SCTLR_EL1.C 关闭的那部分读路径，
  或关闭 D-cache 后走旁路/PTW 的读仍受扰），该方向缓解无效。
- 公开 erratum 库（HIP08 RU-prefetch、#1980005 IDC 等）与本例签名不符，均非本例根因。

## 9. 根因结论（分层陈述）

| 层次 | 结论 | 置信度 |
|---|---|---|
| 直接原因 | `LDR X20,[X0,W25,SXTW#3]` 返回错误数据 → 野指针 `cpu_rq(146)` → `LDR X23,[X27,#0x120]` 翻译故障 panic | **确证**（代数闭合+内存对照） |
| 机制层 | CPU 179 核内取数通路间歇性返回错误数据：LSU 加载结果错（本案，含字节错位形态）、PTW 页表项读错（73 次 WARNING）、偶发多寄存器相继受扰（08-14/08-24） | **确证**（多案多形态汇聚） |
| 物理层 | CPU 179 为 defective/mercurial core：硅片级缺陷致数据通路（L1D 数据阵列/LSU 对齐装配/公共返回路径之一）间歇失效；RAS 不可见；进行性恶化 | **高度可信**（排除法完备；子块定位需厂商手段，超出转储证据边界） |
| 软件责任 | 无。内核代码按规范执行，所有被引用的内存内容均正确 | **确证** |

## 10. 处置建议

**紧急（现在）**
1. 将 CPU 179 下线：`echo 0 > /sys/devices/system/cpu/cpu179/online`（或
   `isolcpus=179` + `nohz_full`，若需保持拓扑）。**仅隔离用户态不够**——本案 5 次
   panic 全部发生在内核线程/空闲均衡路径，必须彻底 offline。
2. 验证有效性：offline 后观察 WARNING 是否绝迹（历史频率约 1–34 次/开机周期）。

**短期**
3. 安排整机检修：向 OEM/海思提交本报告与两份 vmcore，要求对该核做 at-speed scan/
   characterization，按批次缺陷流程 RMA CPU 或主板。同批次的姊妹节点建议排查。
4. 临时兜底监控：周期性扫描 dmesg 关键字 `Ignoring spurious kernel translation fault`
   （它是本故障的前兆信号，出现即应触发下线动作，勿等 panic）。

**不建议**
5. 继续依赖 `l1d_disable`（SCTLR_EL1.C 清位）作为缓解——实证无效（§8）。
6. 更换内核版本/回退补丁——软件无辜，无意义。

## 12. 微架构级根因分析与设计建议（追加，2026-08-25 深度追问）

### 12.1 "右移一位"的物理精确定义

经 `crash vtop` 翻译（本开机内核镜像映射于节点0低段）：

| 项目 | VA | PA | 64B行内偏移 | L1组¹ | L2组² |
|---|---|---|---|---|---|
| 请求的数据 entry[146] | ffffb378e29e5a60 | `0x2ef8be5a60` | 0x20 | **105** | 361 |
| 实际交付的字节窗口 | ffffb378e29e55d1 | `0x2ef8be55d1` | **0x11（非对齐）** | **87** | 343 |
| （参照）entry[0] | ffffb378e29e55d0 | 0x2ef8be55d0 | 0x10 | 87 | 343 |

¹ 假设 TaiShan V110 L1D=64KB/4路/64B 行，组号=PA[11:6]；² 假设 L2=512KB/8路，组号=PA[15:6]。

三个关键事实：
1. 交付字节窗口 = `PA[0x2ef8be55d1 .. +8)` —— 一个**非对齐**窗口（行内偏移 0x11）；
2. 该窗口与请求地址**不同 L1 组**（105 vs 87）、相距 0x480 字节（18 行）；
3. 因此"way 误选/组冲突命中"类故障**不充分**——那会返回对齐正确的别路数据；
   唯一能同时产生"错误源 + 错位一字节"的位置是**阵列读出之后的字节装配/通道转向级**。

### 12.2 取数流水线逐层裁决

| 层级 | 裁决 | 证据 |
|---|---|---|
| 地址生成 AGU/加法器 | ✅ 正常 | x27=x1+x20 代数闭合；后续 [x27,#288] 的 FAR 与保存寄存器精确一致 |
| TLB/本次翻译 | ✅ 正常 | FAR 记录完整正确 EA；错误发生在数据返回而非翻译 |
| Tag 比对/way 选择 | ❌ 不充分 | 12.1 事实 2 |
| 阵列读出/ECC 校验 | ⚠️ 在其之后 | 移位拼装的数据若过 ECC 必报 UE/CE；实测 RAS 全静默 ⇒ 腐化插入点位于**校验之后**的装配 mux/返回通路 |
| **字节装配/通道转向控制** | 🎯 **病灶层** | 同时满足全部签名（见 12.3） |
| 架构态写回 | ✅ 正常 | pt_regs 三份副本一致、与代数自洽 |

### 12.3 统一模型：数据返回 steering 的控制状态瞬时受扰

同一病灶可解释本案全部三种发作形态：

| 形态 | 案例 | 控制受扰方式 |
|---|---|---|
| 整字移位拷贝 | 本案 x20 = entry[0]>>8 | 装配窗口控制整体错源且错位 1 字节，全四拍稳定错误 |
| 高低半字撕裂 | 08-14 x20 = d93715ba_0000ffff | 控制在两半拍之间切换 → 上/下半字来自不同源 |
| 整字读零 | 15:42 x20 = 0 | 窗口选择指向无效位置 → 全零填充 |

反向排除：
- **固定存储单元坏位**（stuck-at cell）：应每次以相同方式读坏相同数据——与"每次形态互异"矛盾；
- **静态数据线缺陷**：应在固定比特位翻转、全机同路径流量大面积异常——未观察到；
- **宇宙射线 SEU**：不会跨周持续、不会钉死单一逻辑核、不会单调恶化——三项均不符；
- **控制触发器瞬时受扰/时序边缘失稳**：恰好产生上述三类离散表现 ✓，且与 PTW 受扰共享上游。

### 12.4 PTW 同源性

73 起 level-0 翻译故障 = 页表遍历读 PGDE 瞬间拿到错误值。线性映射仅个位数 PGD 表项，
63/73 起集中于 CPU179 本节点对（0x6xx…）地址段 ⇒ 绝大多数是**同一两个极热的 PGD 物理字**
被间歇性误读。LSU 加载与页表遍历在核内共享数据返回资源（装载旁路/填充装配/返回总线），
两者同时受扰 ⇒ 公共上游即 12.3 的控制路径，进一步收窄病灶范围。

### 12.5 恶化趋势的物理含义

首症时间 29h→47h→14min→28min→7min 单调恶化 + 形态多样化 ⇒ 渐进性硅退化
（TDDB/电迁移/HCI/阈值漂移一类），先在时序边缘偶发、后加重。**非一次性软错误。**

### 12.6 给芯片设计的可执行建议

**DFT / 验证**
1. 对数据返回装配级的列选择/字节通道 steering 控制（选择寄存器、解码器、拍间保持锁存）
   补齐 stuck-at + transition + at-speed delay 的 ATPG pattern 覆盖审计；
2. 该控制路径加奇偶校验或三模冗余表决；禁止单秩控制锁存驱动多拍突发装配
   （防撕裂）——每拍重采样的双秩寄存；
3. 数据保护检查点后移至最终装配 mux 之后（端到端），或引入 CHI DataCheck/DataPoison
   全链路传播，使装配后腐化可被捕获而非静默交付。

**RAS 架构**
4. 将核内 datapath 纳入 RAS 记录覆盖（本例证明 HIP08 核内为完全盲区：EC=0x25 DABT，
   无任何 SError/GHES 记录）；高可靠模式提供加载影子重读比对（double-sample compare）。

**工程筛查 / FA**
5. 失效样品做 at-speed scan/LBIST（重点：列选择解码器 pattern）、V/f shmoo 表征、
   电压应力 burn-in 筛选；同批次姊妹整机排查；最终物理失效分析(FA)定位退化单元。
6. 软件侧验证实验设计（无需厂商工具即可执行）：在 CPU179 上运行已知常数数组自检负载，
   变量化——物理页着色（组索引）、访问对齐、load 宽度、L1 命中/缺失、SMT 兄弟活动、
   V/f 角点——记录错误率曲面；配合既有 gem5-fi 注入框架，对 byte-steer 控制逐周期
   注入翻转，验证三类签名（移位/撕裂/零）能否复现，反推控制路径位宽与时序窗口。

*边界声明：以上为转储证据约束下可达的最深推断层；确切到具体门电路需失效样品物理分析。*

### 13.2 假设空间的完备性

命题："CPU179 上的一次加载返回了错误数据。" 任何机制必居以下之一——
**(a)** 数据在存储介质中本来就是错的；(b) 用的地址不是想要的（生成错/翻译错）；
(c) 地址正确但读到了错误的内部位置（tag/way 误选、阵列列错）；
(d) 数据读对了但在返回装配途中被替换/变形；
(e) 外部瞬态扰动（粒子翻转等）；(f) 观测工具链失真。
据此定义假设：

- **H1** 存储内容错误（DRAM 单元缺陷 / 被写入坏值）
- **H2** 地址生成错误（AGU/加法器）
- **H3** 地址翻译错误（TLB/本次遍历）
- **H4** tag/way 误选（组内命中到别的路）
- **H5** 阵列静态缺陷（存储单元/读出列固定性坏点）
- **H6** 返回装配控制受扰（ECC 校验点之后的字节通道转向/对齐 mux/旁路控制的瞬态失控）
- **H7** 外部瞬态扰动（SEU 等）
- **H8** kdump 捕获失真

### 13.3 逐假设裁决

**H1 存储内容错误 —— ❌ 否证**
- 推论 P1.1：若持久性缺陷，转储读同地址应见坏值；若曾被写坏，须存在写者。
- 比对：转储实测内容正确（F1）；该数组启动后无任何代码路径改写，亦无 DMA 目标可能；
  且 PGDE 为多核共享页表字——其余 191 核持续读同一物理字从未出错（F5/F7），
  排除"瞬时介质错且恰好自愈"的残余解释。
- 结论：介质无辜，错误产生于读取方核内。

**H2 地址生成错误 —— ❌ 否证**
- 推论 P2.1：若加法器/AGU 出错，则 x27≠x1+x20 或 FAR≠x27+0x120。
- 比对：四次 panic 代数全部精确闭合，FAR 全部一致（F8）。
- 附带否证：即便对 x20 加载本身，AGU 错址也只会取到**对齐**的其他四字；
  无法产生 F2 的非对齐窗口。

**H3 本次翻译错误 —— ❌ 否证**
- 推论 P3.1：翻译层出错应表现为 FAR 异常或取回"某对齐 PA 的对齐数据"。
- 比对：FAR≡EA 精确成立（F8）；交付数据为非对齐窗口（F2），任何 VA→PA 映射整体替换
  都不可能产生字节级错位。PTW 受扰是真实存在的另一类受害事件（F5），
  但不是本次加载的出错机制。

**H4 tag/way 误选 —— ❌ 不充分**
- 推论 P4.1：组内误选应返回**同组其他路、对齐完好**的整四字。
- 比对：F3 显示源窗口属另一组且非对齐。要同时解释需"选错组 + 错位装配"
  两个独立控制错——其中后者已属于 H6 层级。故 H4 作为独立根因不成立，
  其残差并入 H6。

**H5 阵列静态缺陷 —— ❌ 否证**
- 推论 P5.1：固定坏位/坏列应给出确定性、可重复的同位翻转（相同地址×数据→相同错值）。
- 比对：三案三形态（移位拷贝/撕裂/全零，F4）互不相同，且实收值不是真值的任何小汉明距
  扰动，而是**另一位置数据的精确拷贝**——静态布线缺陷无法解释。
- 推论 P5.2：阵列若在 mux 前做 ECC 校验，拼装错数据必触发 CE/UE 上报。
- 比对：RAS 全静默（F6）⇒ 要么校验点之后才腐化（即已承认 H6 层级），要么无覆盖。
  无论何者，"静态单元坏位"均被否证。

**H6 返回装配控制受扰 —— ✅ 唯一幸存**
其可检验推论与全部八项证据一一对应（详见 13.4）：
稳态选错 → 整窗错源+错位（F1/F2/F3 ✓）；拍间切换 → 半字撕裂（F4 ✓）；
选择无效 → 全零（F4 ✓）；发作窗口跨多操作 → FAR/寄存器一字节差、单 panic 多寄存器
同时异常（F4、§7 注 ✓）；共享返回资源 → PTW 同时受害（F5 ✓）；插入点在 ECC 后 →
静默（F6 ✓）；核私逻辑 → 跨开机钉死单核（F7 ✓）；边缘时序路径退化 → 首症时间缩短（F7 ✓）。

**H7 外部瞬态扰动（SEU）—— ❌ 否证**
- 推论 P7.1：事件应在核间空间随机分布；P7.2：发生率近似恒定、无单调恶化趋势；
  P7.3：签名应为相对真值的小汉明距位翻转。
- 比对：100% 钉死单核（F7）、单调恶化（F7）、交付值是别处数据的相干拷贝而非位翻转
  （F2）——三条全部相反。

**H8 kdump 捕获失真 —— ❌ 否证**
- 推论 P8.1：捕获失真应使 FAR 与保存寄存器不一致、各副本互异。
- 比对：FAR≡x27+0x120 精确成立、三份副本一致（F8）。

### 13.4 幸存假设 H6 的内部结构与统一投影

H6 陈述：CPU179 核内、位于数据保护校验点**之后**的数据返回装配通路中，
控制状态（字节通道选择/窗口起点/拍序保持）发生间歇性瞬时失控。

四种观测形态是同一失控机制的四个投影：

| 投影 | 机制 | 证据 |
|---|---|---|
| 整窗错源且错位一字节 | 选择控制在整个四拍内稳定指向错误源+错误起点 | F1/F2/F3（本案） |
| 高低半字撕裂 | 选择控制在上下半字两拍之间切换 | F4（08-14） |
| 整窗读零 | 选择指向无效位置，填充零 | F4（15:42） |
| 发作窗口跨操作 | 同一微秒级窗口内多条数据移动相继受扰（含异常保存路径） | F4（FAR 高字节差、bio 案 x1/x3 同坏） |

反向完备性：固定存储坏位只能给投影一的一种退化形式且不可变；静态线缺陷只能在固定位
翻转；SEU 不能产生他址相干拷贝。**只有控制状态失控能自然生成全部四种投影**——
这是接受 H6 的核心归纳支撑。

### 13.5 H6 的子假设（病灶子块）与判别约束

- **S1** L1D 命中路径旁路/转发 steering；**S2** 缺失路径 fill-buffer 装配；
  **S3** LSU 与 PTW 共享的按拍返回总线/通道 steering；**S4** store-forwarding 通路。
- 约束一（共享性）：PTW 同时受害（F5）⇒ 病灶位于与遍历器共享的资源（倾向 S3，
  或 S1/S2/S3 共同上游的控制供电/时钟域）；
- 约束二（命中/缺失未知）：案发那次加载命中与否无法从转储追溯 ⇒ S1/S2 在本案内不可判别；
- 约束三（机理倾向）：恶化趋势（F7）+ 形态多样 ⇒ 更符合**边缘时序路径的老化漂移**
  使控制触发器采样失稳，而非永久性逻辑损坏。

判别实验（无需厂商工具）：常数数组自检负载 × {页着色(组号)、访问对齐、load 宽度、
命中/缺失强制、SMT 兄弟压力、V/f 角点} 的错误率曲面；gem5-fi 对 steering 控制
逐周期注入翻转，验证四种投影能否复现并反推控制位宽/时序窗口。

### 13.6 最底层物理驱动（开放，超出转储证据能力）

P1 栅氧化层 TDDB；P2 电迁移（通孔/连线）；P3 HCI/NBTI 时序漂移；P4 封装内互连退化。
四者均与"渐进恶化+单核+时序边缘失稳"相容，转储不可判别，需失效样品物理分析(FA)定位。

### 13.7 可反驳性清单（何种新证据将推翻本章结论）

1. 发现对涉事字的任何合法软件写者，或其余任一核复现同类腐化 → 推翻"单核硬件"定性；
2. 在对齐位置找到与实收值逐字相同的内存内容且存在可信寻址路径 → 重开 H2/H4；
3. 厂商扫描在该核外发现可致同签名的公共资源缺陷 → 修改 S3 归属；
4. 任一案例中出现"实收值为真值的小汉明距翻转"且形态固定可重复 → 重开 H5。

### 13.8 结论分层（置信度随层级递减）
